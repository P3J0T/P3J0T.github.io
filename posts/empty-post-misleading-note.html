An Empty POST and a Misleading Note

25 Sep 2026

How a request lost its body—and a correct explanation lost an important detail.

A small POST upload survives a 307 redirect intact. Change the response to 303 and the next request becomes an empty GET. Then a callback changes the method back to POST. The destination receives a POST with no body.

The callback restored the method after the redirect handler had already discarded the data. Following that sequence through the code explains the result. It also leads to a less obvious problem: Qwen could explain the behavior correctly, then save a note that contradicted the source it had just read.

Where the body goes

The relevant code sits in Axios and its dependency follow-redirects. The local reproduction uses a tiny upload, hello redirect, over Node HTTP/1. The server consumes the whole upload before replying. A redirect received halfway through an upload remains a separate question.

The input stream produces two chunks, hello and redirect, once. After a 307, both requests contain all fourteen bytes, although the generator has produced only two chunks in total.

Axios transforms the request data before its adapter selects the transport and pipes the stream into it. With redirects enabled, follow-redirects handles the request. Its write method keeps each chunk in _requestBodyBuffers while writing it to the current request. A redirected request can then replay those retained chunks.

That explains how the body travels twice without rewinding the stream. The counting transformRequest callback also ran only once in each recorded case, including a three-redirect chain: redirects stayed inside the transport.

What happens to the retained body depends on the method and status:

Initial method Redirect Final method Final body
POST 307 POST hello redirect
POST 308 POST hello redirect
POST 302 GET empty
PUT 302 PUT hello redirect
PUT 303 GET empty
POST 303, callback restores POST POST empty
POST 307 → 303 → 307 GET empty

The rewrite condition applies to POST under 301/302, and to methods other than GET and HEAD under 303. It changes the method, clears the body and removes content-related headers. The callback runs afterward. Changing the method there cannot recover the deleted buffer entries.

The mixed chain follows the same history: the first 307 replays the body, the 303 discards it, and the last 307 preserves the resulting empty GET.

What the tools showed

Once _requestBodyBuffers was identified, exact search located its storage, replay and clearing assignments. Broader search offered starting points, with some detours: one embedding-and-reranking query put an HTTP/2 helper first for this HTTP/1 question. Reading the conditions and assignments completed the picture.

Joern gave a partial view. In queries selected separately from Qwen's attempts, it found a static candidate path from the initial data parameter to the first write argument, but no path to the later replay argument. Both endpoints resolved. The body nevertheless replayed in the local request. The empty graph result left that route unresolved; the reason for the missing path was not established.

Qwen's own Joern attempts used different queries and did not establish the complete replay route either. One never reached a flow query after invalid endpoint selections. Both still explained the behavior from source inspection.

A correct answer, a misleading note

One Qwen investigation correctly explained the POST/PUT distinction, then saved this title:

POST vs PUT with 302: both change to GET, body dropped.

The details underneath correctly said that PUT remains PUT. The note also linked to the actual source condition.

After a conversation summary, Qwen reopened that source, rejected the claim that every method changes to GET, and remembered the deferred early-response question. But it declared that the checkpoint needed no correction. The title stayed wrong.

The source link had done its job. It led back to the right passage. Nothing about that made the sentence attached to it true.

This was not confined to one workflow. A plain-tools checkpoint misleadingly implied that transformed data applied only to the first hop. In another run, the answer corrected a citation while the saved note kept the old one.

Across eight Qwen investigations, all eight explained the central behavior correctly. There were two runs per toolset, ranging from ordinary search and a checkpoint file to structured notes, embeddings, reranking and Joern. None passed the broader review of source grounding, scope and saved conclusions. The useful answer and the record left behind were separate outcomes. This was a small, instructed comparison; the individual results show where each run fell short.

A separate retry exercise exposed the same loss in just two words. Qwen described exactly N+1 sends where the source allowed up to N+1: early success could end the loop. Dropping that qualification changed the claim. In a later retry run, the model saved revised notes but left their evidence and caveat fields empty. The continuity follow-up records those separate cases.

On returning to a note, there are two useful things to check: does the saved title still agree with the source condition, and did a correction actually reach the stored note? Reading the replacement back is a way to check that. Merely reopening the source had already left a contradiction untouched.

For the empty POST, the detail worth carrying forward is the order of two events: the body was cleared, then the callback restored the method. Lose that order, and the explanation becomes as confusing as the original behavior.
