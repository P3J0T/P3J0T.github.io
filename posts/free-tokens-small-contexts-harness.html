Free Tokens, Small Contexts, and Why the Harness Matters

17 Aug 2026

Self-hosting changes the economics of using a model. It does not magically fix the model.

I have been working on Awoki, a harness for long-running software and security investigations. The project grew out of a fairly simple problem: even when a model is good enough to be useful, a long investigation tends to expose everything around the model that is not.

Context gets compacted. Earlier evidence loses its meaning. Search results get promoted into facts. A repository changes while old conclusions are still being cited. A hypothesis slowly becomes a finding because nobody explicitly marked the transition.

Those are easy problems to call “model limitations”. Some of them are. But many are also system-design problems.

“Free” tokens change the bottleneck

With an API, every exploratory branch has a visible price. With a model running on hardware you already own, the marginal cost of another few thousand tokens can feel close to zero. Obviously the hardware, electricity, time and maintenance are not free. Hence the quotes.

But the change in behaviour is real. You can search more, retry more, ask the model to inspect another file, run another pass, or follow a weak lead without watching a token meter.

Then another resource becomes much more obvious: context.

You can have effectively abundant generation and still have a finite working memory. Even models advertising very large context windows do not make every token equally useful, and local deployments often run at smaller practical contexts because memory and latency matter.

Cheap tokens are not the same thing as durable memory.

The harness is part of the intelligence

There is a tendency to evaluate an AI system as if the model were the whole product. I think that becomes less useful as soon as you start doing real work with it.

A model has shortcomings. Short context. Weak tool discipline. Inconsistent persistence. Bad retrieval choices. Formatting quirks. Long-horizon drift. Sometimes excessive confidence. Sometimes excessive refusal.

The obvious response is to wait for a better model. Another response is to ask a different question:

How much of a model's weakness can be moved out of the model and fixed by the harness?

If the model forgets which repository it is investigating, software can store that. If it cannot reliably carry an entire investigation through compaction, durable state can carry the useful parts. If semantic retrieval finds something that merely looks relevant, the harness can force the workflow back to exact source before treating it as evidence.

This is one of the ideas behind Awoki. Model context is temporary working memory. Project state should not be.

retrieval     -> discovery
source        -> evidence
model         -> reasoning
verification  -> stronger claims
continuity    -> survival across context loss

None of this makes the model smarter in the benchmark sense. It can still make the combined system substantially more useful.

Fix model shortcomings, but do not build a cathedral around them

There is an obvious failure mode here too. Once you start compensating for model behaviour, it is easy to build layers of orchestration for problems that do not really exist, or for problems the next model release already handles better.

That is why the current Awoki work is mostly stabilization and usefulness testing rather than feature expansion. If a mechanism does not help a realistic investigation, I would rather simplify it or remove it.

Do not spend model intelligence on deterministic problems. Do not spend software complexity on imaginary model problems either.

That balance is more interesting to me than trying to build a giant agent framework.

Local models are getting good enough for this to matter

Recent Qwen 27B-class releases are a good example of how quickly this space is moving. Capable open-weight models in this size range are arriving fast enough that a specific version number can become stale almost immediately. The important part is the direction: models that are realistic to run on serious local hardware keep getting better at coding, repository work, tool use and general reasoning.

That does not mean “27B is all you need”. It means the floor keeps moving. Models that an individual, researcher or small team can plausibly operate are becoming capable enough that the quality of the surrounding system starts to matter a lot.

The model is also replaceable. Awoki is not a Qwen runtime and is not tied to one provider. That is intentional. If a better model appears next month, continuity, source provenance, retrieval boundaries and verification do not suddenly become useless.

Security has another reason to care about local control

Security research is a strange workload for general-purpose assistants because understanding dangerous behaviour is often literally the job.

Reverse engineering, exploit analysis, malware research, protocol work and red-team exercises routinely require discussing techniques that look suspicious when stripped of authorization and context. Hosted systems have to make policy decisions for a huge population of users, so legitimate specialist work can sometimes hit those boundaries.

Locally hosted, less-restrictively aligned or community “uncensored” models can be useful here—not because “anything goes” is a good security model, but because the operator controls the environment and the policy boundary.

I would rather think about controls at several layers:

model        -> reasoning engine
harness      -> state, tools, evidence, workflow constraints
environment  -> isolation, permissions, network boundaries
human        -> authorization, scope, judgement

Removing a remote refusal layer does not require removing every other control. For professional red-team and reverse-engineering workflows, moving some control closer to the operator can actually make the boundaries more explicit.

Awoki is an experiment in that direction

Awoki is not “memory for AI”, and it is not an autonomous security researcher. It is a Docker-first harness around OpenCode for long-running, evidence-backed software and security work.

The user still drives the investigation. Retrieval helps discover code; exact source remains authoritative. Important observations can be promoted into durable state. Claims can retain provenance. Compaction can restore a bounded working set instead of pretending the chat transcript is a database.

The project has become less about adding clever mechanisms and more about finding which ones actually earn their complexity.

That is also why self-hosting is interesting here. If tokens become cheap enough to use freely, we can spend them on exploration. If context remains constrained, the harness has to decide what deserves to survive. If the model has rough edges, we can sometimes engineer around them. If the harness becomes more complicated than the problem, we can delete parts of it.

Building in the age of AI

I do not think the interesting end state is everybody talking to one giant general-purpose model.

I expect a lot of the useful work to look more like systems built out of models: security workflows, coding environments, research tools, personal knowledge systems, automation pipelines, operations tooling, domain-specific assistants, and things we do not have good names for yet.

The model will matter. So will the harness, tools, state, data, permissions, verification and the human workflow around it.

We are not only entering the age of AI models. We are entering the age of building with AI.

Different models. Different constraints. Different harnesses. Different jobs.

The question I find more interesting than “which model wins?” is: what can we build once models are components?

Awoki is an ongoing project. This post describes the ideas behind the approach, not a claim that the problems above are solved.
